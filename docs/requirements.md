# 简易 TCP 连接探测服务：需求文档

## 1. 项目概述

本项目使用 Rust 实现一个 HTTP 服务。客户端提交一个或多个探测目标后，服务在后台解析目标地址并尝试建立 TCP 连接，客户端再通过任务 ID 查询执行状态和各目标的探测结果。

本项目仅判断目标地址的指定端口能否在限定时间内建立 TCP 连接，不实现 HTTP 健康检查，也不使用第三方封装好的网络探测组件。

## 2. 目标与范围

### 2.1 核心目标

- 提供 HTTP 接口接收探测任务。
- 后台异步执行探测，提交任务时不等待全部探测结束。
- 使用 TCP 连接判断连通性，不发送应用层数据。
- 单个任务支持批量目标，各目标独立执行、独立返回结果。
- 对任务提交接口进行简单限流。
- 提供清晰的参数校验、任务状态和错误信息。

### 2.2 本期范围

- IPv4、IPv6 地址和域名目标。
- 可配置的单目标连接超时时间。
- 内存任务存储和固定数量的后台执行 worker。
- 基于客户端 IP 的任务提交限流。
- 服务自身健康检查接口。

### 2.3 非目标

- ICMP Ping、UDP 探测、端口扫描和路由追踪。
- HTTP/TLS 协议检查、登录认证或业务健康检查。
- 用户系统、权限管理、任务持久化和分布式调度。
- 任务取消、重试、定时探测和结果推送。
- 图形化管理界面。

## 3. 关键约定

- 一次 TCP 连接成功即表示探测成功，连接随后立即关闭。
- 连接被拒绝、超时、DNS 解析失败及其他网络错误均表示探测失败，但不会影响同任务中的其他目标。
- 任务提交和结果查询分离，避免大量或慢速目标长期占用 HTTP 请求。
- 一个任务包含 1～100 个目标；同一任务中允许重复目标，不去重。
- 单个目标的超时时间默认为 3000 毫秒，可配置范围为 100～10000 毫秒。
- 所有时间戳使用 UTC 的 RFC 3339 格式，耗时使用毫秒。
- 第一版任务与结果只保存在内存中，服务重启后全部丢失；完成任务默认保留 1 小时。
- 服务默认面向受信任的内网环境，不内置认证。部署到不受信任网络前，应增加认证、授权和访问控制。

## 4. 功能需求

### 4.1 提交探测任务

客户端通过 `POST /api/v1/probe-tasks` 提交任务。

每个目标必须包含：

- `host`：非空主机名或 IP 地址，不包含协议、路径和端口；IPv6 地址不使用方括号。
- `port`：1～65535 的整数。

任务可包含：

- `timeout_ms`：该任务中每个目标的 TCP 连接超时时间。
- `targets`：目标数组，长度为 1～100。

处理规则：

1. 校验 JSON 格式和全部字段；任一目标不合法则拒绝整个任务，不创建部分任务。
2. 创建任务并生成全局唯一的任务 ID。
3. 将任务放入有界队列，立即返回 HTTP 202 和任务 ID。
4. 后台 worker 获取任务，逐个或并发执行其中的目标探测。
5. 队列已满时返回 HTTP 503，避免任务无限堆积。

### 4.2 后台 TCP 探测

每个目标依次执行：

1. 将域名解析为一个或多个 IP 地址；字面量 IP 无需 DNS 解析。
2. 尝试与解析得到的地址建立 TCP 连接。
3. 任一地址在超时时间内连接成功，则该目标探测成功。
4. 所有地址均失败或超时，则该目标探测失败，并记录适合客户端理解的错误类别。
5. 记录开始时间、结束时间和实际耗时。

约束：

- 直接基于 Rust TCP 和 DNS 能力实现，不调用 `ping`、`nc` 等外部命令。
- 不使用第三方封装好的探测组件。
- 不发送业务数据，不读取目标响应。
- 单目标失败不得导致任务或进程退出。
- 全局并发探测数应有限，默认最多 10 个目标同时探测，防止资源耗尽。

### 4.3 查询任务与结果

客户端通过 `GET /api/v1/probe-tasks/{task_id}` 查询任务。

返回内容：

- 任务 ID、任务状态和提交、开始、结束时间。
- 目标总数及已完成的数量。
- 每个目标的原始参数、执行状态和探测结果。
- 成功时记录耗时；失败时记录错误类别和简要错误信息。

任务状态：

- `queued`：已创建，等待执行。
- `running`：已开始执行，仍有目标未完成。
- `completed`：所有目标均已完成，无论单个目标成功或失败。

目标状态：

- `pending`：尚未执行。
- `running`：正在执行。
- `success`：TCP 连接成功。
- `failed`：TCP 连接失败。

任务状态只表示调度进度，不使用 `partial_success` 表示部分目标失败；目标是否可达应查看各目标结果。

### 4.4 限流

- 仅限制任务提交接口，结果查询和健康检查不计入提交限流。
- 第一版按直接连接的客户端 IP 进行固定窗口限流。
- 默认每个客户端 IP 每分钟最多提交 10 个任务，窗口从该客户端首次提交时开始计算。
- 一个批量任务只计为一次提交，不按目标数量重复计数。
- 被限流时返回 HTTP 429、明确的错误信息和 `Retry-After` 响应头。
- 不根据 `X-Forwarded-For` 等请求头识别客户端，避免伪造；如需经反向代理部署，应在后续单独设计可信代理规则。
- 限流状态保存在内存中，服务重启后重置。

### 4.5 健康检查

提供 `GET /health`，用于判断 HTTP 服务进程是否可用。

- 正常时返回 HTTP 200 和 `{"status":"ok"}`。
- 该接口不代表任何被探测目标可达。

## 5. 错误处理

- 请求体不是合法 JSON、字段类型错误或字段值越界：HTTP 400。
- 任务 ID 不存在或结果已过期：HTTP 404。
- 触发提交限流：HTTP 429。
- 后台任务队列已满：HTTP 503。
- 未预期的服务端错误：HTTP 500，不向客户端泄露内部实现细节。
- 错误响应统一包含机器可读错误码、人类可读信息和请求 ID。
- 单目标网络错误记录在目标结果中，不改变查询接口的 HTTP 200 状态。

## 6. 非功能需求

### 6.1 可靠性

- 后台任务Panic或单个目标失败不应导致服务退出。
- 所有外部输入均有长度、数量或取值限制。
- 任务队列、并发数、任务保存时间和限流均应有边界。
- 服务重启导致内存任务丢失属于本期已知限制。

### 6.2 性能与资源

- 提交接口只进行校验、限流和入队，不执行网络探测。
- 默认最多 10 个目标并发探测，避免批量任务耗尽文件描述符或线程资源。
- 默认单目标超时 3000 毫秒，防止连接无限等待。
- 完成的任务默认保留 1 小时，并定期清理。

### 6.3 可观测性

- 记录服务启动、监听地址、任务创建、任务完成和未预期错误。
- 日志包含任务 ID 和请求 ID，便于关联排查。
- 不记录请求体中的无关敏感信息。

### 6.4 可维护性

- HTTP 层、任务管理、TCP 探测和限流逻辑分层，便于独立测试。
- 配置项集中管理，支持命令行或环境变量覆盖默认值。
- 文档中的字段、状态和错误码与实现保持一致。

## 7. 验收标准

1. 服务启动后，健康检查返回 HTTP 200。
2. 提交单个合法目标后，立即获得 HTTP 202 和任务 ID。
3. 对本地明确开放的 TCP 端口进行探测，最终结果为目标 `success`。
4. 对本地明确关闭的端口进行探测，最终结果为 `failed`，任务仍为 `completed`，且错误类别可辨识。
5. 同一任务提交多个目标时，每个目标均有独立结果，单个失败不影响其他目标。
6. 域名、IPv4 和 IPv6（运行环境支持时）目标均能按约定处理。
7. 空目标列表、超过 100 个目标、非法端口和非法超时均返回 HTTP 400，且不创建任务。
8. 任务执行期间查询可看到 `queued` 或 `running` 及完成数量，执行结束后可看到完整结果。
9. 不存在的任务 ID 返回 HTTP 404。
10. 同一客户端连续提交超过限流阈值后收到 HTTP 429 和 `Retry-After`。
11. 任务过多导致队列满时返回 HTTP 503，服务仍可处理后续查询。
12. 不使用第三方封装好的探测组件，不依赖外部探测命令。
13. `cargo fmt --check`、`cargo clippy --all-targets -- -D warnings` 和 `cargo test` 均通过。
